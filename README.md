[![CI](https://github.com/jcrussell/solvent-streets/actions/workflows/ci.yaml/badge.svg?branch=main)](https://github.com/jcrussell/solvent-streets/actions/workflows/ci.yaml)

Pure Go CLI for pavement data ingestion, hex-grid coverage analysis, PCI decay forecasting, and MapLibre visualization.

- No CGO — pure Go SQLite and geometry
- Single SQLite database, multi-city
- WASM interactive forecast in the browser
- Static site export or live server

**Live showcase:** <https://joncrussell.com/solvent-streets/> — metro areas rendered from the configs in [`examples/`](examples/), plus a [50-largest-US-cities](examples/top-50-cities/) national sample.

## Install

pvmt is not in any Linux distribution's package repositories. Pick one of the options below.

### Debian/Ubuntu package

Download the `.deb` for your architecture from the [latest release](https://github.com/jcrussell/solvent-streets/releases/latest), then install it:

```
sudo apt install ./pvmt_<version>_linux_amd64.deb
```

The package installs `pvmt` to `/usr/bin` and ships shell completions and manpages.

### Pre-built binary (any Linux)

Download the tarball for your architecture from the [latest release](https://github.com/jcrussell/solvent-streets/releases/latest), extract it, and move the binary onto your `PATH`:

```
tar -xzf pvmt_<version>_linux_amd64.tar.gz
sudo mv pvmt /usr/local/bin/
```

### Build from source

Requires Go 1.26+ (see [CONTRIBUTING.md](CONTRIBUTING.md) for prerequisites).

```
git clone https://github.com/jcrussell/solvent-streets
cd solvent-streets
make build
```

The binary is written to the repo root; copy it onto your `PATH` as above.

### `go install` (no export or serve)

```
go install github.com/jcrussell/solvent-streets/cmd/pvmt@latest
```

This builds everything except the interactive forecast WASM, which is
generated by `make` and not part of the published module. Ingest, compute,
forecast, status and the rest work; `pvmt export` and `pvmt serve` refuse to
run and point you at one of the options above.

## Quickstart

Create `pvmt.toml`:

```toml
[[cities]]
name = "Alameda, CA"
overpass = true
```

Live view of a single resource:

```
pvmt roads ingest
pvmt roads compute
pvmt serve
```

Open http://localhost:8080.

Full pipeline — all resources and a deployable static site:

```
pvmt all ingest
pvmt all compute
pvmt export -o ./site
```

`./site` is a self-contained folder you can deploy to GitHub Pages or any static host. `pvmt forecast` prints deterioration and cost projections in the terminal over every jurisdiction's pavement: the dashboard's "All" view, not its headline, which covers city-maintained pavement when the city has any. It, export and serve all simulate the forecast from the computed data when they run, so it is not a pipeline step.

`pvmt all ingest` and `pvmt all compute` also pull fire stations from OpenStreetMap and compute a per-hex fire response time over the road network (the map's **Color by → Fire response**); `pvmt services --help` runs those steps on their own. Parking lots carry an estimated space count, and the gear menu's tag filters narrow the city list by metro group and state on every page.

Use `pvmt --help` and `pvmt <command> --help` for full usage.

See [`examples/`](examples/) for ready-to-use configs covering several US metro areas and a 50-largest-US-cities national sample.

### Publishing the showcase

The site at <https://joncrussell.com/solvent-streets/> is a single consolidated dashboard: one `pvmt export` run from [`examples/all/`](examples/all/pvmt.toml), whose `[[include]]` blocks union every other example into one config (277 cities) and tag each one at the include site. Cities are browsed by tag rather than by example; the gear menu's tag filters (one per dimension — metro group, state, …) narrow the city selector on every tab and scope the Compare and Aggregate tabs. See [docs/configuration.md](docs/configuration.md) for `tags` and `[[include]]`.

Ingest/compute/forecast cannot run in CI (the source SQLite DB is ~1 GB and Overpass/ArcGIS pulls are slow and rate-limited), so the publish runs from a developer machine that already has data in `~/.local/share/pvmt/pvmt.db`. The combined config covers every example's cities, so they must all have data first — but it does **not** need its own ingest: a city reached through `[[include]]` keeps the identity of the file that declared it, so `examples/all` reads exactly the rows and snapshots each example's own ingest/compute wrote.

```
cd examples/<name> && pvmt all ingest && pvmt all compute   # per example; hours, only when data is stale
make site     # renders ./site/ from your local DB
make deploy   # force-pushes ./site/ to the gh-pages branch
```

Running ingest or compute from `examples/all` is supported and writes into those same per-example namespaces — which means it *replaces* their data rather than sandboxing it. Prefer running per example unless you specifically mean to refresh everything.

GitHub Pages picks up the new commit on the next sync. The site auto-routes to `/solvent-streets/` under the `joncrussell.com` CNAME owned by the user-pages repo.
